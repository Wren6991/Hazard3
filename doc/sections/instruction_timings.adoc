[[section-timings-m]]
=== Integer Multiply and Divide (M)

This table assumes the core is configured with: <<param-MULDIV_UNROLL>> = `2`, <<param-MUL_FAST>> = `1`, <<param-MUL_FASTER>> = `1` and <<param-MULH_FAST>> = `1`.

[%autowidth.stretch, options="header"]
|===
| Instruction | Cycles | Note
3+| 32 {times} 32 -> 32 Multiply
| `mul rd, rs1, rs2` | 1  |
3+| 32 {times} 32 -> 64 Multiply, Upper Half
| `mulh rd, rs1, rs2` | 1 |
| `mulhsu rd, rs1, rs2` | 1 |
| `mulhu rd, rs1, rs2` | 1 |
3+| Divide and Remainder
| `div rd, rs1, rs2` | 17 to 19 | Depending on sign correction
| `divu rd, rs1, rs2` | 17 |
| `rem rd, rs1, rs2` | 17 to 19 | Depending on sign correction
| `remu rd, rs1, rs2` | 17 |
|===

Changing these configuration parameters has the following effects on execution timings:

* <<param-MUL_FASTER>> = `0`: Fast multiplier latency increases from 1 to 2. Throughput remains at 1/cycle.
* <<param-MULH_FAST>> = `0`: High multiplies execute on the sequential multiply/divide circuit instead of the fast multiplier. `mulhu` has the same timings as `divu`. `mulh` and `mulhsu` have the same timings as `div`, plus one additional sign correction cycle when all 32 low-word bits are zero and the overall result is negative.
* <<param-MUL_FAST>> = `0`: All multiplies execute on the sequential multiply/divide circuit. `mul` has the same timings as `divu`.
* <<param-MULDIV_UNROLL>> = `1`: All instructions on the sequential multiply/divide circuit execute 16 cycles slower.
* <<param-MULDIV_UNROLL>> = `4`: All instructions on the sequential multiply/divide circuit execute 8 cycles faster.

[[section-timings-c]]
=== Compressed Instructions (C or Zca)

All C extension 16-bit instructions are aliases of base RV32I instructions. On Hazard3, they perform identically to their 32-bit counterparts.

A consequence of the C extension is that 32-bit instructions can be non-naturally-aligned. This has no penalty during sequential execution, but branching to a 32-bit instruction that is not 32-bit-aligned carries a 1-cycle penalty, because the instruction fetch is cracked into two naturally-aligned bus accesses.

[[section-timings-zilsd]]
=== Load/Store Pair (Zilsd)

[%autowidth.stretch, options="header"]
|===
| Instruction | Cycles | Note
3+| Load/Store Pair
| `ld rd, imm(rs1)` | 2 | Issues as two `lw`.
| `sd rs2, imm(rs1)` | 2 | Issues as two `sw`.
|===

To avoid stalls, you should conservatively schedule `ld` as though it always has a 1-cycle load-use delayfootnote:data_dependency[]. Whether this delay actually occurs depends on which register in the pair is loaded last. If the base register `rs1` is an odd-numbered register, the odd register in the `rd` pair is loaded last. Conversely if `rs1` is an even-numbered register, the even register in the `rd` pair is loaded last. This parity rule ensures a trap on the second load in the pair can determine the load address even when `rd` aliases `rs1`. The load-use delay occurs only when the next instruction depends on the last-loaded register. See also <<section-64-bit-bus-access>>.

[[section-timings-zcb]]
=== Additional Basic Compressed Instructions (Zcb)

Similarly to the C extension, this extension contains 16-bit variants of common 32-bit instructions:

* RV32I base ISA: `lbu`, `lh`, `lhu`, `sb`, `sh`, `zext.b` (alias of `andi`), `not` (alias of `xori`)
* Zbb extension: `sext.b`, `zext.h`, `sext.h`
* M extension: `mul`

They perform identically to their 32-bit counterparts.

[[instruction-timings-branch-predictor]]
=== Branch Predictor

Hazard3 includes a minimal branch predictor, to accelerate tight loops:

* The instruction frontend remembers the last taken, backward branch
* If the same branch is seen again, it is predicted taken
* All other branches are predicted nontaken
* If a predicted-taken branch is not taken, the predictor state is cleared, and it will be predicted nontaken on its next execution.

Correctly predicted branches execute in one cycle: the frontend is able to stitch together the two nonsequential fetch paths so that they appear sequential. Mispredicted branches incur a penalty cycle, since a nonsequential fetch address must be issued when the branch is executed.
